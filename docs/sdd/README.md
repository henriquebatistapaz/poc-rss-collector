# Canonical SDDs for this Project

This directory holds feature specs in SDD (Software Design Document) format — the source of truth for functional and technical requirements.

## How to use

**One directory per spec** — all artifacts of a feature live together:

```
docs/sdd/
├── constitution.md · TEMPLATE.sdd.md · INDEX.md · README.md    (shared, root level)
├── usage.log                   project-level AI usage: /ai-init setup, /retro, /metrics, /tech-debt
└── <kebab-case-name>/          e.g. oauth-authentication/
    ├── spec.md                 the SDD (follows TEMPLATE.sdd.md)
    ├── test-plan.md            generated by /test-plan
    ├── usage.log               AI usage per run, one appended line:
    │                           `<ISO datetime> | <prompt> | model: <model> | in: ~<tokens> | out: ~<tokens>`
    └── ...                     feature diagrams, ADRs, anything spec-scoped
```

1. Create `docs/sdd/<name>/spec.md` following the template (from an issue, use `/spec-from-issue` — it does this for you).
2. Register every SDD in `INDEX.md`.

Specs do NOT get a prompt file each — the cycle prompts (`/test-plan`, `/implement-spec`, `/validate-implementation`, `/open-mr`) take the spec path as input. Dedicated prompts in `.github/prompts/` are reserved for recurring procedures (runbooks, deploy guides).

## Principles

The project's immutable rules live in `constitution.md` — every SDD must honor them.

## Minimum conventions

- Context and problem
- Goals and out of scope
- Functional and non-functional requirements
- Architecture and decisions
- Implementation plan
- Acceptance criteria (verifiable)
- Risks and rollback
